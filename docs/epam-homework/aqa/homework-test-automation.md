### Відповідний напрям

Нам відповідає **Напрям 1: Груповий pre-order**, бо реалізовано й інтегровано
Backend/Frontend. Останній frontend перевірено на localhost зі справжнім API,
але ще не опубліковано на CloudFront. Перед приймальним E2E-запуском потрібно
розгорнути саме перевірену версію frontend. Напрям 2 повністю не вимагається.

| Рівень | UI-сценарії | API-сценарії/підготовка |
| --- | --- | --- |
| 1 | Owner бачить учасників, страви, суми, draft та порожні кошики; оновлення після змін гостя | Створення даних, права Owner проти інших ролей/гостя/anonymous, неіснуюча та порожня група |
| 2 | Консолідація однакових страв, виключення draft, Submit, замовлення у Waiter | Кожна причина відмови окремо; повторний Submit; не-Owner; перевірка фінального стану |
| 3 | Remove Guest, перерахунок і повний шлях до замовлення без видаленого гостя | Submitted/останній/чужий/відсутній учасник;403/401 за чинним контрактом; чужий 400/відсутній 404 |

### Загальні вимоги до майбутньої реалізації

- README починається з напряму та обраної архітектури. Фреймворк можна обрати;
  специфікація не зобов'язує використовувати лише BDD/Screenplay. Згаданий
  `aqa/restaurant-aqa-framework` отримано в наступному вкладенні й імпортовано; стан див. [Preparation.md](Preparation.md).
- Основні сценарії проходять реальний UI; авторизацію/валідацію та підготовку
  даних перевіряємо через API. Unit-тести не підміняють E2E.
- Динамічні майбутні дати, незалежні та ізольовані дані, прибирання через наявні
  API або документовані унікальні префікси, якщо видалення не підтримується.
- `.env.example` без реальних адрес/паролів; приватна `.env` і CI secrets.
- Звіти та failure artifacts (скриншот/відео/trace), CI, фільтри за рівнем/тегом.
- Формулювання «впалий тест не зупиняє пайплайн» потребує явної політики:
  продовжити виконання/збір артефактів, не приховувати ненульовий статус тестів.
- Рівень із зірочкою: Report Portal + хмарний пайплайн, AWS або інший провайдер.
  Його розгортання/вартість ще не погоджено; ресурси не створено.

### Уточнення контрактів перед написанням тестів

У README слід розрізняти API total усіх сесій та UI Grand Total лише
підтверджених кошиків/збереженого Owner preorder. Також врахувати створення
Owner-сесії: «ще ніхто з гостей не приєднався» не завжди означає відсутність
Owner у відповіді після bootstrap. Не міняти працюючі контракти лише для
зручності E2E й не називати ці випадки перевіреними до фактичного запуску.

Рівні, архітектура та зірочка ще не обрані користувачем. Тести й CI ще не
реалізовано; цей запис лише зберігає завдання і початковий розбір.
